# Architecture Spine Review — Rubric Walker

## Overall verdict

For a solo hobby/personal project, this spine is well-calibrated: it correctly avoids inventing enterprise concerns (no SSO, no multi-tenant, no RBAC), covers all 20 PRD FRs in the Capability → Architecture Map, and the seven ADs fix the genuinely divergence-prone decisions (content-as-jsonb vs blocks table, tree representation, sync protocol, auth vendor strategy, repo layout, view-as-page-attribute). Stack versions are grounded in dated, same-day web verification recorded in the memlog rather than asserted from training data. The one real hole is exactly the kind of thing this document exists to prevent: the FE↔BE authentication boundary (how a JWT issued by Auth.js in the frontend gets verified by the backend Guard, and how it physically crosses the wire for both REST and WebSocket) is asserted but not actually specified, leaving two independently-built halves free to make incompatible assumptions. Secondary gaps exist around sync reconnection semantics and a backup/storage cross-reference, both fixable with small additions rather than a rewrite.

## Findings

- **critical** Auth token verification contract unspecified (§AD-5) — AD-5 states Auth.js issues a JWT in the frontend and the backend "chỉ verify JWT qua Guard riêng," but never specifies the shared signing secret/algorithm/JWKS the two independently-hosted services must agree on. This is compounded by a real technical trap: Auth.js v5's default session token is an encrypted JWE (A256GCM), not a plain signed JWT — a generic NestJS `JWT Guard` using `jsonwebtoken`/`passport-jwt` cannot verify it out of the box without deliberately reconfiguring Auth.js's `jwt.encode`/`decode` to emit a standard signed token. If this isn't caught before implementation, FR-1 (the first MVP feature, gating everything else) breaks at integration time. *Fix:* Add a rule to AD-5 (or a new AD) naming the concrete token format (e.g. "Auth.js configured via custom `encode`/`decode` to issue a plain HS256 JWT with shared secret `AUTH_SECRET` env var, not the default encrypted session token") so both sides build against the same contract.
- **high** Token transport across the FE→BE boundary is undefined for both REST and WebSocket (§Consistency Conventions, §Structural Seed) — the conventions table says "JWT lưu trong httpOnly cookie" but never states whether the backend reads that cookie directly (requiring same-site/shared-domain cookies across two separate Docker services) or expects an `Authorization: Bearer` header attached by a frontend proxy layer. The structural diagram's `FE -->|proxy API/WS| BE` arrow implies Next.js proxies WebSocket traffic to the backend, which standard Next.js (no custom server, Turbopack/App Router deploy mode as chosen in the Stack table) does not do trivially — WS proxying usually needs a reverse proxy (nginx/Traefik) or a custom Node server, neither of which is decided here. *Fix:* Pick one topology explicitly (e.g., "browser connects to BE's WS gateway directly over WSS; only REST is proxied through Next.js route handlers, which attach `Authorization: Bearer <token>` read server-side from the Auth.js session") and state it as a rule, not just a diagram arrow.
- **medium** AD-4 covers live broadcast + last-write-wins but not reconnect-reconciliation (§AD-4) — FR-10's PRD consequence explicitly requires that a session which was offline during a change "khi có mạng lại, dữ liệu đồng bộ về đúng trạng thái mới nhất, không tạo bản sao/không xung đột im lặng." AD-4's rule only describes broadcasting to sessions that are currently connected; it has no rule for what a reconnecting client must do (re-fetch current state via REST vs. server replaying missed events). Two stories could diverge here — one assuming push-only is sufficient, one assuming a refetch-on-reconnect handshake. *Fix:* Add a line to AD-4: e.g. "On WS (re)connect, client MUST issue `GET /api/v1/pages/:id` for any page it has open before trusting further push events" (or equivalent explicit reconciliation rule).
- **medium** FR-14 backup scope not cross-referenced against deferred FR-9 storage decision (§Deferred, §Structural Seed) — the structural seed diagram already commits to a specific backup mechanism (`CRON: pg_dump daily, giữ 7 bản`), which only covers the Postgres database. The Deferred section separately leaves "local disk volume vs S3-compatible storage" open for FR-9 image uploads. If that later resolves to local disk, uploaded images sit outside the pg_dump backup path, silently breaking FR-14's promise that "toàn bộ dữ liệu Workspace được sao lưu." *Fix:* Add a note (in Deferred or as a constraint on the FR-9 decision) that whichever storage backend is chosen for FR-9 must be included in the backup rotation, or must itself be inherently durable (e.g., S3 versioning) if excluded from pg_dump.
- **low** Two unconfirmed decisions surfaced only in the memlog, not resolved before finalization (.memlog.md line 23) — the run log itself flags "AD-7 (Database View = thuộc tính Page...) và Redis-not-needed-at-this-scale là quyết định mới phát sinh khi distill spine, chưa hỏi user trực tiếp - cần xác nhận ở bước triage," but no subsequent memlog entry records that confirmation happening before the spine draft was written (next entry just announces the draft is done). Both calls are sound on their own merits, but they were promoted from "self-inferred" to "decided AD" without the flagged triage step completing. *Fix:* Either add a memlog entry recording the user's confirmation, or mark AD-7 and the Redis note as provisional pending sign-off.
- **low** FR-1's testable lockout consequence has no home in the data model (§AD-5, ERD) — the PRD requires "sai mật khẩu 5 lần liên tiếp → khóa tạm đăng nhập trong 15 phút," which needs persisted state (failed-attempt counter, lockout-until timestamp), but neither the `USERS` ERD entity nor AD-5's rule mentions where this lives. Low severity since it's purely backend-internal state with no cross-unit divergence risk, but it's a PRD consequence with no architectural coverage at all. *Fix:* Add `failed_login_attempts` / `locked_until` (or similar) to the `USERS` ERD entity, or note it as backend-internal and out of spine scope.
- **low** Stack table mixes version strings with descriptive prose (§Stack) — every row states an actual version number except `TanStack React Query` and `Zustand`, whose "Version" column instead holds usage notes ("server-state cache, invalidate khi nhận WS event (AD-4)" / "local UI state ... — không lưu server-state"). Harmless but inconsistent with the rest of the table and slightly obscures that no version was actually verified for these two libraries.

## Mechanical notes

- AD numbering is continuous (AD-1 through AD-7), no gaps or duplicates.
- Every AD has all three required fields (Binds / Prevents / Rule) present and non-empty; none are vague truisms — each names a concrete artifact (schema column, gateway, event name, library) and a concrete failure mode it blocks.
- Frontmatter `binds: [FR-1 … FR-20]` matches the PRD's FR range exactly (FR-1 through FR-20, no gaps, no extras).
- Capability → Architecture Map contains a row for every FR from FR-1 to FR-20; nothing from the PRD is silently unmapped. Deferred rows (FR-14 seed, FR-16, FR-17–FR-20) correctly point back into the Deferred section rather than dead-ending.
- Cross-references resolve cleanly: every "(AD-n)" citation in the Capability Map and Consistency Conventions points to an AD that exists in the Invariants section; no dangling references found.
- `companions: []` is appropriate — no companion doc content (e.g., detailed schema spec) is implied elsewhere that's missing here.
- Version-verification entries in `.memlog.md` are dated the same day as the spine (2026-07-29) and read as genuinely web-checked (Next.js 16.2.x, NestJS v11, PostgreSQL 18.4, Node 24 LTS, Tiptap 3.29.x, Prisma v7.4.2, Auth.js v5 with an explicit caveat about the Better Auth merger) rather than asserted from stale training data — this is the strongest part of the artifact's grounding.
